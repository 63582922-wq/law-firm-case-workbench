# 律师办案 Agent 项目审计与整改建议

日期：2026-09-05。性质：代码、工作流和交付证据审计；不是商用验收通过记录。

## 需求理解与审计结论

用户要求的成果是：律师交代案件目标并上传材料后，系统主动阅读、发现事实冲突和争点、寻找并核对依据、调用工具计算、提出有条件的攻防方案、起草可编辑应诉材料；律师处理实质判断、修订和最终批准。用户不应承担运行调度、错误对账或反复登录的工作。

判断：当前主要障碍在项目架构、能力约束、交付链衔接和开发方法。模型有已记录的实质性错误，但尚无同输入、同工具、同评分标准的模型对比，因此不能把迟迟不可用主要归因于某个模型，也不能声称换模型即可解决。

项目有真正的 Agent 基础组件：语义规划、任务图编译、持久任务、工具适配、快照变更重规划、记忆、来源校验。它不是完全没有 Agent 代码。但首发应诉路线把部分自主能力收缩成固定流程，正常用户从材料到成果的完整能力尚未被证明。历史响应恢复件不构成这条正常路径的替代品。

## 高优先级发现

### A1：首发应诉路径的输入和计划过度固定

证据：`backend/case_kernel/controlled_defence_case_agent_planner.py` 的 `_CONTROLLED_DEFENCE_OBJECT_TYPES` 只保留代理档案、事实、诉请、已核验法源、已批准规则；投影把程序事件置空。`_controlled_proposal` 首轮固定两个任务，`_controlled_sources` 要求事实/诉请已确认、法源/规则已锁定。`backend/case_api/case_agent_worker_entrypoint.py:627` 将该路由接入生产 Worker，并在 658 行启用过滤。

影响：需要形成答辩状时，系统先要求人或上游流程准备相当多的结构化内容；这一分支本身没有完成原始材料阅读、发现未知争点、寻找缺失法源的动态工作。通用规划器仍存在，不能由此推断全项目所有路径都固定，但首发用户价值受到了直接影响。

建议：保留确定性任务编译器和权限控制，把应诉模板改成默认目标和检查项，不作为固定任务图。让同一任务会话按材料、缺口及工具观察结果继续推进；未确认事实可以用于明确标识的分析假设，不得晋升为正式事实。正式计算、立场批准和提交继续受硬门控制。

### A2：禁止模型生成正式金额，被扩大成禁止模型理解数值

证据：`case_agent_lawyer_analysis.py:2491` 的提示词禁止所有自由文本中的数值；2682 行开始对来源标题、正文和 signals 做数值替换。请求在 430 行附近只有 messages 和结构输出合同，没有让这次分析自行调用工具补回量化上下文的循环。

本轮用当前真实函数执行的合成文本投影：

原文：借条记载205,000.00 CNY，银行到账200,000.00 CNY；转账日期为2019年11月15日。

模型所见：借条记载【金额事实乙】，银行到账【金额事实甲】；转账日期为【日期事实丙】。

影响：数值标签保存了引用身份，但丢失具体金额、日期及其语义；不能据此充分比较差异规模、日期关系和适用期间。提示词同时禁止采用规则参数，进一步削弱有依据的分析。不能靠换更强模型恢复从输入中删掉的信息。

建议：允许模型读取经过授权、来源绑定的原始数值。模型只能提出计算请求或引用计算结果 ID；工具用版本化代码计算，文书编译时注入正式数字。把“候选推理”和“正式结果”分开约束。禁止越权写入，而不是全面删除分析输入。

### A3：一个任务失败，整案容易停在等待人处理

证据：`case_agent_supervisor.py:1611` 把任一 FAILED 任务映射到 WAITING_INPUT；`decide_next_commands` 在 1140 行对该状态直接返回空命令。UNKNOWN 有独立对账路径，这部分应保留。现有实现也有安全重试策略，不能说完全没有恢复机制。

影响：已知格式错误、局部解析失败和真正需要律师决定的事项被过度汇总为等待输入；可继续的独立工作容易一起停止。律师看到的“等待补充信息”未必真是其能解决的问题。

建议：将失败分为可本地修复、已知可重试、外发结果未知、材料缺失、律师判断和系统故障。前两类在已有授权与有限预算内处理；UNKNOWN 先对账；只有后几类需要相应角色介入。保留原始失败事件，以新的尝试/修订记录恢复，不能覆盖历史。为不依赖失败节点的任务提供继续执行及部分成果交付。

### A4：验收输入已经替 Agent 做了关键事实发现

证据：`backend/scripts/run_managed_defence_acceptance.py:769` 写入五条人工整理的合成事实，包括借条与到账金额差异、外币不能直接合计、周转款性质待定；随后逐条用 `FactStatus.CONFIRMED` 确认。脚本还配置诉请、应对立场和法源。

影响：上传 88 页并不等于模型独立读懂 88 页。该验收可证明已整理事实上的分析与系统接线，不能证明从原始材料自动发现这些问题。不是认定脚本作弊，而是必须缩窄它所能支持的结论。

建议：把基础设施夹具、原始材料端到端任务和律师质量评审分开。端到端任务只提供原始材料、代理角色和目标；事实、争点和参考答案仅供评估者使用。冻结一组独立保留样本，改变金额、时间、材料顺序、缺失情况和案件角色后验证，不继续围绕同一失败样本写专用通路。

### A5：动态交付清单与前端终审条件不一致

证据：`backend/case_api/web_case_agent_control.py:341` 根据激活计划取得交付种类，支持 DEFENCE_STATEMENT。`web/src/lib/web-active-plan-execution.ts:3` 却固定要求 CASE_REVIEW_MEMO 和 PAYMENT_LEDGER；`canCompleteActivePlanRun` 要求两种文书均打开且四种文件均下载。`web-agent-panel.tsx:735` 复述了相同固定要求。

影响：仅包含答辩状的合法计划可能永远无法满足前端终审条件。此为源码可推导的条件冲突，本轮未做浏览器复现。

建议：前后端共用来自当前运行的交付清单，由服务端提供每项需要的审阅动作；审阅决定绑定具体版本。下载成功只能说明取得文件，不能作为实际读过并认可内容的证明。

### A6：文书可下载，不等于律师修改闭环完整

证据：`case_agent_document_revisions.py` 把模式设为 DETERMINISTIC_TEMPLATE_REVISION；`web_case_agent_documents.py:264` 的修订参数只有身份、对象、版本和幂等键，没有修改正文或修订要求。前端主要呈现“更新到当前模板”。

影响：这条修订链能重编译模板，但不能单独支持“律师改了答辩理由→Agent 根据修改重写→比较差异→重新批准”。不可把模板更新等同于完整编辑能力。

建议：增加段落级批注/修订指令或修改后文件回传、差异比较、事实与引用重新绑定、重新渲染和批准失效。先选择一种完整编辑路径打通，而非同时实现多个半成品编辑器。

### A7：可追溯校验与法律分析质量评估需要分开

证据：`case_agent_verifier.py:876` 的律师包分支解析合同并比较声明来源与任务来源集合。这证明来源归属和结构，不能单独证明某句话确实由该证据支持。项目另有 golden evaluator，但当前首发验收不能替代独立材料盲测和执业律师质量评估。

建议：分别报告“结构/权限/数字通过”和“分析有依据/无重大遗漏/实质可用”。增加主张—证据支持关系、反证遗漏、对方最强论点、假设条件和文书一致性的评价。用律师修改量和完成任务耗时衡量价值，不能用章节数、引用数或测试数量代替。

### A8：工程交付状态难以归因

证据：当前工作树有大量未跟踪源码及改动；本轮 git 日志最新提交仍为 2026-08-11。此前恢复 API 使用宿主 Python 挂载，ADR-0083 已从规范 Compose 分离，但最新干净发布镜像仍无本轮运行证据。当前 Docker 和工作台均不可连接，磁盘空间远低于构建门槛。

影响：源码、运行镜像、实际界面和历史报告可能不是同一版本。磁盘解释当前不能启动/构建，不能解释此前全部产品能力缺口。

建议：统一实际工作区；整理当前变更为可审阅版本，先排除真实材料和密钥，再建立私有版本提交、可复现构建及单一启动入口。固定一台有足够空间的验收环境，记录源码版本/镜像标识/迁移版本；无需此时拆成更多微服务。

## UI 交互与视觉建议（源码审查，待实屏验证）

### 后续终审边界复核

`web_case_agent_final_review.py` 此前只调用文书读取，不检查返回状态。文书服务在模板过期/生成中时合法返回
不可下载的状态 DTO，因此“没有抛异常”不能证明存在可审阅文件。已修复：检查返回类型、原成果身份、CURRENT、
download_ready、模板版本和 PDF 页数；36 项相关测试通过，非浏览器或真实数据库验收。

另一个尚未修复的实质缺口：`RunFinalReviewApproval` 的 v1 摘要绑定原运行 `state.artifacts`；正文修订通过独立
版本请求/包/回执表生成后继，不必推进 Agent 事件版本。前端 `activePlanReviewEpoch` 同样只依赖运行版本及成果数。
因此不能仅凭已有运行版本或打开/下载过某种文书，就认为律师审过当前修订正文。需要把律师实际审阅的文书版本和
文件指纹纳入终审命令，服务端对当前包事务核验并写入不可变批准；本次状态页修复不解决这个绑定缺口。

1. 目标输入要求用户同时填写目标、完成标准和边界，见 `web-agent-panel.tsx:703`。建议以“准备应诉材料、评估案件风险、检查对方证据”等任务预设预填完成标准；高级约束可展开。律师应提供业务信息，不必学习提示词工程。
2. 页面直接显示“GET 核验”“原请求编号重放”“Worker”“封存响应恢复候选”等实现细节。改为“正在恢复结果”“需要系统管理员处理”“历史分析，仅供参考”，技术证据放入详细记录。
3. 保留一个案件任务主入口。左侧材料导航，中间证据/文书阅读，右侧与当前位置相关的分析、出处和批注；案件首页优先显示重大风险、待律师决定和最新成果。
4. `case-workbench.module.css:947-990` 的分析正文、文书表格、来源标签存在 8–11px 字号。建议正文以 14–16px 为起点、表格至少 12–14px，并在 1280/1440 宽度、长中文文件名和浏览器 200% 缩放下验证。此处是样式风险，不是已经证明的实际可读性失败。
5. 现有纸色、墨绿、衬线标题有一致的案卷风格，建议保留主方向，优先修正密度、层级和持续阅读体验。未看到运行页面，不对“高级感”、实际对比度或完整无障碍做虚假评分。
6. 一项任务失败时明确显示：哪些成果已完成、哪些受影响、系统正在做什么、律师到底需要决定什么。不要只剩不可点击按钮或笼统“等待输入”。

## 整改顺序与停止条件

以下是待实施建议，不是已完成工作。最终商用目标保持不变。

| 次序 | 交付目标 | 验收证据 |
|---|---|---|
| 1 | 收敛一个真实主流程，修复动态交付清单和文书修订断点，恢复稳定环境 | 从同一工作台可交办、观察、查看成果、修改、复核；所有步骤对应同一版本 |
| 2 | 调整推理输入与工具边界，恢复受控的动态执行循环 | 原始材料中的未预填冲突由 Agent 发现；数字调用工具；补充材料后只更新受影响结果 |
| 3 | 对已知失败进行有限恢复和部分交付 | 可恢复错误无需管理员手动改库；未知外发不重复发送；历史事件不改写 |
| 4 | 独立样本和模型诊断 | 同材料/工具/预算比较分析结果；区分阅读遗漏、模型推理、工具失误和控制器误拒绝 |
| 5 | 律师用户验收及商用发布 | 原始材料到可编辑应诉材料完整走通，记录律师修改和耗时；完成隔离、备份恢复与发布证据 |

每个整改项先锁定具体失败，再做对应复核和一次用户路径验证；通过后推进下一项。只有新增失败或代码变化才追加验证。不要把“一次模型调用”限制当作产品必须遵守的长期架构；应使用总费用、工具次数、时间和停滞次数上限约束真实多步任务。

不建议从零重写。保留已有证据不可变、租户/案件权限、确定性计算、私有对象库、任务持久化与审计、文书渲染能力；重点重整它们之间的用户任务链。不要优先增加多 Agent 角色数量、更多专用恢复脚本或新视觉皮肤。

- `web/src-tauri/gen`

项目磁盘占用从约 876 MiB 降至 826 MiB，约回收 50 MiB。删除项可重建，但不在回收站。未删除源码、Git 历史、当前依赖、案件原件、模型响应、数据库卷或验收产物。项目外 Codex 会话数据未触碰。

保留的主要占用：前端依赖约 489 MiB、后端环境约 148 MiB、历史 outputs 约 147 MiB。为了回收不足 1 GiB 而删除当前依赖，会使开发环境再度不可用，之后安装还会占回空间。

建议长期控制规则：构建缓存按重建能力清理；测试成功时只保留结构化结果、版本和必要截图；失败样本保留最小复现及原始响应；重复渲染中间件经核验后清理。历史验收记录应先建立包含原路径、内容哈希、运行状态和恢复方法的归档清单，再压缩迁移；没有通用引用检查前，不批量移动 `outputs/`。真实案件资料使用独立保留策略，不能混入开发缓存清理。
