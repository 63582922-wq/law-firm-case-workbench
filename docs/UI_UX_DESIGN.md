# UI、交互与视觉设计计划

## 1. 体验目标

律师进入系统后，不应先看到聊天框，而应立即知道：

1. 当前案件处于哪一步；
2. 最近发生了什么变化；
3. 哪些事项已经获得律师确认；
4. 哪些内容只是 AI 候选；
5. 哪一项决定正在阻止案件继续；
6. 完成下一步会影响哪些结果；
7. 离形成可提交材料还有多远。

北极星体验：

> 每个页面都让律师更快做出一个可追溯的专业决定，而不是让律师阅读更多 AI 文字。

## 2. 设计原则

### 案件工作台，不是聊天机器人

主 Agent 以右侧上下文助理、下一步建议和解释层出现。主要任务通过证据页、表格、差异、审批和文书界面完成。

### 先证据，后结论

任何事实、交易、法条或文书段落都可以点击回到来源。来源预览不应要求跳出当前工作上下文。

### 状态必须准确

状态按领域分组，不把不同含义压成一套“全局七状态”：

| 状态域 | 机器状态 | 主要 UI 文案与动作 |
|---|---|---|
| 案件流程 | `CREATED…READY_TO_EXPORT/EXPORTED/ARCHIVED` | 当前阶段、前置条件、可进入下一阶段的动作 |
| 运行 | `PROCESSING/NEEDS_DECISION/CONFLICTED/BLOCKED/STALE/FAILED_RETRYABLE/FAILED_MANUAL/STALE_RESULT` | 处理中、待决定、有冲突、已阻断、结果过期、可重试失败、需人工处理、旧结果未应用 |
| 审批 | `DRAFT/PENDING/APPROVED/REJECTED/EXPIRED/SUPERSEDED` | 草稿、待审批、已批准、已拒绝、已过期、已被新版本替代 |
| 派生件有效性 | `VALID/STALE/REVOKED/ARCHIVED` | 有效、已失效、已撤销、已归档；失效/撤销件禁止正式使用 |
| 提交包生命周期 | `DRAFT/QA_READY/LOCKED/EXPORTED` + 独立 current 指针 | 草稿、待终审、已锁定、已导出；是否“当前有效”单独显示 |
| 外部请求 | `PREFLIGHT_REQUIRED/AUTHORIZED/SUBMITTED/SUCCEEDED/FAILED_RETRYABLE/FAILED_MANUAL/UNKNOWN_SUBMISSION/CANCELLED` | 待授权、已授权、已提交、成功、可重试、需人工、提交状态未知、已取消 |

机器枚举、中文文案、颜色、图标、允许动作和阻断行为在 Phase 0 状态矩阵中一一映射，Phase 1 原型只能使用该矩阵。

“AI 已生成”不能使用代表完成的绿色状态。绿色只表示人工复核或明确批准。

### 一次只突出一个重要决定

案件首页将“下一项律师决定”放在视觉首位。大量低风险信息进入次级区域，不制造告警墙。

### 高风险操作显示影响

批准法律规则、确认付款性质、锁定提交版、撤销锁定和删除申请，都必须在执行前展示：

- 将发生什么；
- 影响哪些文书和计算；
- 是否可撤销；
- 谁能执行；
- 执行后下一步是什么。

## 3. 信息架构

### 全局导航

```text
案件
待办与审批
知识库
模板
团队质量
设置
```

### 案件内导航

```text
案件总览
材料与证据
主体与身份
诉请与争点
事实与时间线
交易台账
法律依据
利息计算
文书工作室
提交中心
审计记录
```

页面导航不按系统技术模块命名，而按律师完成案件的自然顺序命名。

## 4. 全局布局

v1 只提供桌面 Web 工作台，建议在 1440px 宽度设计，1280px 保证完整工作。移动端查看、审批、锁定和导出均不在 v1 范围内，避免在设备与再认证方案完成前形成高风险旁路。

标准布局：

```text
┌ 律所 / 案件 / 全局搜索 / 用户 ┐
├ 案件阶段条与程序期限 ─────────┤
│ 左侧案件导航 │ 主工作区 │ Agent侧栏 │
│               │          │ 可收起     │
└ 状态、保存、来源与审计提示 ───┘
```

证据和文书类页面允许全屏工作模式。

## 5. 关键页面

### 5.1 案件列表

目标：快速识别临近期限、等待本人决定和存在阻断的案件。

显示：

- 案名、案号、法院、案由；
- 当前阶段；
- 最近送达与最近期限；
- 当前责任人；
- 下一项决定；
- 阻断数和已失效结果；
- 最近活动。

默认不展示虚荣指标或模型调用次数。

### 5.2 新建案件与材料上传

采用渐进式流程：

1. 选择本方角色和案由；
2. 填写最少案件信息；
3. 拖入整个案件文件夹或文件；
4. 显示上传范围、文件类型、总大小和安全说明；
5. 上传后后台解析，用户可以离开；
6. 完成后进入材料盘点，而不是直接生成答辩状。

错误需逐文件说明：损坏、加密、格式不支持、疑似恶意内容、重复上传。

### 5.3 案件总览

第一屏从上到下：

1. 程序期限与可靠性：送达来源、期限规则版本、确认状态；在送达方式、地域、节假日和起算规则经律师确认前只显示“期限候选”，不显示可依赖剩余时间；
2. 下一项律师决定：问题、证据、可选操作、影响；
3. 案件阶段：已完成、当前、阻断、后续；
4. 材料健康：缺失、解析失败、待复核；
5. 核心数字：本金、原告诉请、已付款候选、正式计算状态；
6. 最近变更及下游失效；
7. 主 Agent 简报。

### 5.4 材料与证据工作台

三栏布局：

```text
文件/页面列表 | 原始页面查看器 | 抽取、标记与来源关系
```

必须支持：

- 缩略图和页面虚拟化；
- 原件/派生件醒目标识；
- 精确重复、疑似重复、相似非重复分组；
- 相关、无关、待确认筛选；
- OCR 文字与页面坐标联动；
- 搜索人物、昵称、账号、金额和交易号；
- 点击记录定位原页并高亮；
- 红框编辑、撤销和对齐检查；
- 生成派生 PDF 前预览页数和来源；
- 显示覆盖原件全部页面的处置清单和进度，未审页面不得被折叠为“无关”；
- 关键主体、借据、法院文书和交易流水显示复核人或抽检状态。

“删除无关页面”在交互中解释为“生成只包含确认相关页的提交派生件”，原件保持不变。

### 5.5 主体与身份

使用实体卡和关系图的组合，但关系图只服务于少量复杂映射，不做装饰性可视化。

每条映射显示：

- 真实姓名；
- 微信昵称；
- 微信号、手机号、银行卡；
- 证据来源；
- 置信度；
- 对方主张、本方主张和律师确认；
- 冲突和历史变更。

### 5.6 诉请与争点

左侧显示起诉状原文和坐标，右侧显示结构化诉请：

- 请求内容；
- 金额、币种和期间；
- 原告依据；
- 本方响应：承认、部分承认、争议、范围异议；
- 支持和反驳证据；
- 举证责任；
- 待律师决定。

任何承认操作都需要高风险确认，不允许 AI 默认勾选。

### 5.7 事实与时间线

时间线不是长篇摘要，而是可过滤的事实对象：

- 日期；
- 事件类型；
- 本方/对方/客观材料；
- 事实状态；
- 证据数量；
- 对哪些争点和文书有影响。

日期不确定时显示区间或“待确认”，不能伪造精确日期。

### 5.8 交易台账

采用专业数据表格，支持冻结列、筛选、批量确认、来源下钻和对账。

核心列：

```text
日期 | 金额 | 币种 | 方向 | 付款方 | 收款方 | 渠道
交易号 | 对方主张 | 本方主张 | Agent建议 | 律师确认
关联借款 | 证据来源 | 备注 | 状态
```

表格底部显示：原始账单合计、纳入台账合计、差异和无法对账项。金额展示统一千分位和两位小数，但保留原始精度。

### 5.9 法律依据

每个候选规则使用“规则卡”，包含：

- 法律命题；
- 本案所需事实；
- 适用/不适用理由；
- 生效和失效期间；
- 法律位阶；
- 精确条文；
- 官方来源和快照哈希；
- 过渡规则；
- 支持、限制或冲突规则；
- 律师批准状态。

用户可以并排比较两个不同法律版本。普通搜索结果和律师文章只能进入“研究线索”，不能出现正式批准按钮。

### 5.10 利息计算工作台

顶部先显示正式计算所需的四类已批准参数：

- 本金事件；
- 利率和适用期间；
- 付款性质；
- 冲抵顺序和舍入规则。

中部显示逐期表格和本金余额曲线；曲线只作为理解辅助，表格是正式结果。

支持内部情景比较，但界面明确：

- “内部测算”不进入法院文书；
- 只有一个情景可以被律师批准为正式情景；
- 情景改变会使哪些文书失效。

每个总额都可以下钻到期间、公式、参数、付款和原始证据。

### 5.11 文书工作室

结构：左侧文书目录，中间正文，右侧来源/审查面板。

段落状态：

- 事实和证据完整；
- 有法律依据；
- 缺少支持；
- 引用已失效；
- 与其他文书冲突；
- 待律师确认；
- 律师已锁定。

律师可以接受建议、直接编辑、评论、退回和查看版本差异。Agent 不能在后台静默改文书。

任何直接编辑都会生成新的不可变版本，并立即将受影响段落的旧批准标记失效。系统对修改文字重新检查事实/证据来源、金额、币种、法条版本和跨文书一致性；只有律师重新批准最终渲染文本哈希后才能锁定提交版。

### 5.12 提交中心

提交中心不是普通下载页，而是发布门：

- 当前唯一提交版状态；
- 文件清单、顺序、页数和哈希；
- 签字、盖章、日期和授权材料检查；
- 姓名、角色、案号、法院、金额、币种和证据编号一致性；
- 未解决阻断；
- 律师终审声明；
- 锁定人、时间和导出记录。

点击“锁定法院提交版”前展示完整影响。锁定后若上游变化，提交版自动变为“已失效，禁止继续导出”。

## 6. Agent交互

Agent 侧栏只显示与当前页面有关的能力：

- 解释当前数据；
- 找出冲突或缺口；
- 提出下一步；
- 生成结构化执行提案；
- 将律师自然语言转成可编辑筛选、规则或草稿修改建议。

每条 Agent 建议包含：

- 建议内容；
- 为什么；
- 使用了哪些来源；
- 置信度或不确定性；
- 执行后影响；
- 接受、修改、拒绝。

Agent 不能通过一句“我已经处理好了”隐藏异步任务、失败、审批或成本。

## 7. 重要交互模式

### 来源回跳

点击事实、金额、法条或段落中的来源标签，在同页面打开源文件、页码和坐标；关闭后保留当前编辑位置。

### 批准

批准不是普通勾选。界面显示批准对象、依据、影响、当前版本和批准人。批量批准只适用于低风险同类项。

### 失效

失效对象保留但禁止用于正式输出。页面解释失效原因、变化来源、影响对象和重新验证入口。

### 冲突

冲突使用并排比较，不只显示“存在错误”。律师可以选择一方、合并、标记未知或要求补充材料。

### 长任务

显示当前阶段、已处理页数、异常数和是否可安全离开。技术失败与语义待决分开呈现。

### 空状态

空状态说明为什么为空、需要什么材料、谁可以处理和下一步。避免泛化插画和“开始探索”式文案。

## 8. 视觉设计方向探索

编码前生成三种视觉方向，三者使用同一个高密度案件首页和证据工作台，不允许只用空白概念页比较。

### 方向 A：现代案卷室

关键词：纸张、墨色、案卷标签、朱批、克制、可信。强调文书阅读舒适度和证据实体感。

### 方向 B：证据控制台

关键词：结构、精度、数据、对账、状态。强调高密度表格、来源关系和风险处理效率。

### 方向 C：专业合议工作室

关键词：协作、批注、审阅、版本、决策。强调承办、协办和复核之间的工作交接。

最终方向可以融合功能优点，但必须先选择一个主视觉语言。不能默认套用通用 SaaS 侧边栏、紫色渐变、圆角卡片海洋或全屏聊天气泡。

## 9. 设计系统计划

建立业务语义 Token，而不仅是颜色 Token：

```text
run.processing
run.needs_decision
run.conflicted
run.blocked
run.failed_retryable
run.failed_manual
run.stale_result
approval.pending
approval.approved
approval.expired
artifact.valid
artifact.stale
artifact.revoked
submission.locked
submission.exported
request.unknown_submission
evidence.original
evidence.derived
evidence.unverified
risk.deadline
action.destructive
```

组件优先级：

- 案件阶段条；
- 下一决定卡；
- 来源标签；
- 审批条；
- 失效影响面板；
- 三栏证据查看器；
- 高密度交易表；
- 规则卡；
- 计算期间表；
- 文书来源边栏；
- 提交清单；
- 版本差异；
- 长任务进度与异常队列。

图标使用成熟图标库，不用 emoji 或自制符号。状态同时使用文字、形状和颜色，不能只靠颜色。

## 10. 可访问性与易用性

目标遵循 [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/)：

- 全键盘操作；
- 明确焦点；
- 正文和关键状态满足对比度；
- 点击区域不小于合理触控尺寸；
- 表格具备列标题、排序和筛选语义；
- 弹窗保持焦点并可退出；
- PDF 页面支持缩放、旋转、文字层和键盘翻页；
- 状态不依赖颜色；
- 数字、日期和币种可被屏幕阅读器正确理解；
- 动效服从减少动态效果设置。

## 11. 设计到开发

1. 用户选择视觉方向；
2. 冻结关键流程和页面状态；
3. 建立设计 Token 和组件清单；
4. 为每个组件写数据、权限、空、错、加载、冲突、失效状态；
5. 前端用真实 Schema 和现实数据密度实现；
6. 每个页面做参考设计与实现截图对比；
7. 修复布局、字体、表格、边距、状态和交互差异；
8. 用真实浏览器完成任务测试；
9. 通过可访问性和视觉回归；
10. 再进入下一批页面。

## 12. UI验收标准

- 用户 10 秒内识别下一项关键决定；
- 用户能区分 AI 候选和律师批准；
- 任意正式事实在两次操作内到达来源页；
- 任意计算总额在三次操作内到达逐期公式和付款证据；
- 上游变化后，失效结果立即显现且不能误导导出；
- 5 名律师中至少 4 名独立完成核心流程；
- P0 旅程键盘可完成；
- 1280px 宽度无关键内容截断；
- 文档和表格长时间阅读不过度疲劳；
- 页面不是通用后台模板，视觉语言与证据、案卷、审阅和审批相匹配。
