# ADR-0018：大案长台账采用案件版本绑定的稳定游标与最小投影

状态：已接受（事实、交易、案件审查摘要及证据来源页已实现；其他长列表待迁移）

## 背景

原案件工作台通过单个快照一次读取全部事实、交易、付款分类及关联字段。数据量增大后，这会同时放大数据库读取、网络响应、浏览器内存和渲染开销。若普通偏移分页期间案件发生写入，客户端还可能漏行、重行或把两个案件版本拼接成一个看似完整的结果。

## 决定

1. 事实与交易列表使用键集分页，不使用 `OFFSET`。事实按 `(created_at, fact_id)`；交易按“有日期优先、日期、created_at、transaction_id”稳定排序。
2. 每页默认 50 条、最多 100 条。游标是严格规范化的 Base64URL JSON，只包含版本、列表类型、案件 UUID、案件版本和排序键；未知字段、重复字段、非规范编码、跨案件或跨列表游标全部拒绝。
3. 游标不是身份凭证，也不签发权限。每一页仍在只读重复读事务中重新核验律所、案件和数据库成员角色；查询始终携带 `firm_id` 与 `matter_id` 条件并受强制 RLS 约束。
4. 首屏先读案件审查摘要，再以 `expected_version` 并行读取事实和交易首批。任一读取发现案件版本变化即返回冲突，前端不拼接。后续页同时受游标内版本和显式预期版本约束。
5. 事实列表仅返回文本、来源、状态和证据定位数量；不返回律师标识或决定哈希。交易列表仅返回日期、金额、币种、状态、证据数量和最新已批准付款性质；不返回付款人、收款人、流水号、渠道或完整证据链接。
6. 中文界面明确显示“已载入 / 总数”，只有确有后续页时显示“继续载入 50 条”。后续页冲突或失败保留已显示内容但明确标为未完成，并提供“重新载入当前案件”；不自动重试或回退合成数据。
7. 原全量 `/snapshot` 暂时保留给尚未迁移的内部调用，但事实与争点页不再依赖它。证据来源页已按 ADR-0019 迁移；诉请/争点超大集合和其他长列表必须按同样原则继续迁移，完成前不得宣称所有大案路径已解决。

## 已验证

- 跨案件、跨列表、篡改、重复字段和非规范游标在数据读取前被拒绝；
- 案件版本变化在读取后续行前返回 409，首屏摘要与两类列表也由同一预期版本绑定；
- 后端分页投影的字段白名单和 SQL 最小字段由单元测试覆盖；
- 中文渐进加载、恢复提示、前端静态检查和生产构建通过；
- 全仓 325 项后端检查通过，4 项专用 PostgreSQL 破坏性检查按安全门跳过。
