# ADR-0050：Web 文书候选必须复用认证隔离渲染器

- 状态：已采纳，实现中
- 日期：2026-09-04
- 关联：ADR-0028、ADR-0040、ADR-0046

## 背景

Web 的“案件核对摘要（Word/PDF）”和“收付款核对表（Excel/PDF）”只允许从服务端已确认的事实、诉请和收付款快照生成。实际浏览器验收发现，页面已展示生成入口，但 Web API 运行时没有接入已部署的隔离 LibreOffice 渲染器；点击后只能得到未完成的泛化错误。把 LibreOffice 装回浏览器 API 进程虽然能暂时生成文件，却会破坏现有的最小网络、最小进程职责和 Office 解析隔离边界。

## 决策

1. Web 文书候选生成只通过既有的 `IsolatedDocumentRendererClient` 调用固定、内网、HMAC 认证的 `document-renderer` 服务；浏览器、案件材料、URL、文件路径和命令均不能影响该连接或渲染命令。
2. Web API 启动时必须对隔离渲染器执行一次已认证健康预检。预检失败则不装配文书候选服务，部署不得把生成能力标记为可用。
3. `api` 容器可加入专用的内部 `document-render` 网络，但不安装 LibreOffice，也不获得外部渲染能力；渲染器仍不暴露给浏览器或网关。
4. 提交前材料核对接口明确投影“文书候选生成是否已配置”。未配置时，UI 说明能力未部署并禁用入口，而不是把失败留给律师点击后发现。
5. 渲染器已知拒绝与结果未知分别返回安全、可行动但不泄露内部细节的状态。结果未知不自动重发；律师必须先刷新候选台账，再决定是否重新发起。

## 后果

- Word/PDF 与 Excel/PDF 候选恢复为真实可验收链路，同时保留生成内容、渲染输出和审阅哈希的同源绑定。
- Web API 多出一个固定内网依赖；其健康状态成为部署前置条件，而不是 UI 假设。
- 本 ADR 仅恢复“律师审阅候选”生成与查看前提，不能把候选等同于律师批准、正式法律结论或法院提交包。
