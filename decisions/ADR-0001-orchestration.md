# ADR-0001：采用代码状态机作为硬总控

状态：`Accepted`

日期：`2026-08-03`

## 背景

产品需要处理证据、诉请、法律版本、金额计算、律师审批、文书和法院提交包。若主 Agent 直接掌控流程，模型的非确定性会影响权限、状态、计算依赖和最终发布，难以稳定复现和审计。

## 决策

1. 代码状态机是最高控制层；
2. 主 Agent 是用户可见的智能案件经理；
3. 专业 Agent 作为有边界的工具被调用；
4. Agent只输出结构化候选和执行提案；
5. 所有状态变化通过经过鉴权、验证和审计的 Command；
6. 金额、日期、文件和一致性由确定性程序完成；
7. 律师审批决定法律路径、计算参数、诉讼立场和提交版。

## 原因

- 法律和金额错误具有高影响；
- 案件过程必须可追溯和重放；
- 需要严格控制跨租户和高风险动作；
- 需要上游变化后准确失效下游结果；
- 不同模型或提示词更新不应破坏案件状态。

## 后果

### 正面

- 权限和审批可证明；
- 流程可测试；
- Agent可以更换而不破坏核心案件；
- 金额和版本可以稳定复现；
- 律师能够控制最终立场。

### 成本

- 需要先设计领域模型和状态机；
- 自由对话不再是主要交互；
- 新增 Skill 时需要Schema、审批和测试；
- 依赖失效图增加开发工作。

这些成本属于产品可靠性的必要成本。

## 被否决方案

### 单一超级 Agent

无法稳定约束计算、状态、权限和来源，不采用。

### 平级多 Agent 群聊和投票

会增加上下文重复、冲突、成本和审计难度；法律正确性不能由多数票决定，不采用。

### 全部写死为代码流程

不能有效处理材料歧义、事实归纳和法律研究，不采用。

## 复核条件

只有出现新的、经过真实案件证明的需求，才重新评估：

- 状态机严重限制必要的专业判断；
- 专业 Agent 需要直接接管完整用户会话；
- 外部系统需要独立的长期工作流；
- 模块达到独立扩容或部署边界。

即使复核，权限、审批、金额计算和唯一提交版仍不得交给大模型。
