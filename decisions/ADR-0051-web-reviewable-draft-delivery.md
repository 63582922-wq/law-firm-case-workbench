# ADR-0051：Web 文书候选必须在批准前提供经认证的审阅与下载

- 状态：已采纳，实现中
- 日期：2026-09-04
- 关联：ADR-0028、ADR-0046、ADR-0050

## 背景

Web 端已经可以登记由隔离渲染器生成的 Word/PDF 或 Excel/PDF 文书候选，但原页面只显示候选元数据和“批准”按钮，不能让律师打开审阅 PDF 或取得可编辑文件。这样会把“可以生成”伪装成可交付能力，也会让律师在没有审阅实际输出的情况下作出批准动作。

现有桌面端的一次性本机授权机制依赖 OS 绑定会话和本地加密文件仓，不能直接搬到浏览器运行时；浏览器运行时使用的是同源、MFA 后的服务端 Cookie 会话和私有对象存储。因此，不能通过暴露对象存储 URL、对象键、文件路径或把桌面访问令牌移植到 Web 来补洞。

## 决策

1. Web 增加同源、经服务端 MFA 会话认证的文书候选交付端点。浏览器只能指定当前案件中已列出的候选对和固定用途 `REVIEW_PDF` 或 `DOWNLOAD_EDITABLE`；服务端自行解析租户、案件、候选状态、对象定位和媒体类型。
2. 每次交付都重新验证当前人类身份、案件读取权限、候选状态、私有对象哈希与文件签名。浏览器永远拿不到对象存储 URL、对象键、加密凭据或原始渲染器地址。
3. 审阅 PDF 使用受限内联响应；可编辑文档使用下载响应。两者均使用 `Cache-Control: no-store, private`、`Content-Security-Policy: sandbox`、同源资源策略和 `nosniff`，并且不从 URL 或文件名接受客户端输入。
4. UI 必须先提供“查看审阅 PDF”和“下载可编辑文档”，并明确候选仍未批准、不可作为法院提交件。批准入口保留给律师的明确后续行为，不由读取或下载自动触发。
5. 文书候选能力只有在“隔离生成器”和“认证审阅交付服务”都已装配时才向浏览器显示为可生成。任一部分缺失时，系统不显示半成品入口。

## 后果

- 律师可以实际打开并核对候选文件，再决定是否批准；候选、批准、正式法院文书和提交包仍是四个不同状态。
- Web API 增加私有对象读取职责，但该读取被固定为已登记候选、固定用途、当前 MFA 会话和完整性校验，不能成为通用对象下载接口。
- 浏览器端体验从“元数据台账”升级为可审阅交付；但没有律师批准、独立 QA 和提交包锁定时，仍不会开放法院提交下载。
- 全局 HTTP 安全中间件只能补齐缺失的默认安全头，不能在响应返回前覆盖已核验文件路由的更严格缓存或内容策略。
