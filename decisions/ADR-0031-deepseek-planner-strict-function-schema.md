# ADR-0031：DeepSeek 规划器使用严格函数 Schema 提交候选计划

状态：已接受（本机受管 Alpha 实现）

日期：2026-08-24

关联：ADR-0027 律师 Agent OS 总控

## 背景

统一 Agent 总控此前通过 DeepSeek `json_object` 模式接收语义计划。真实脱敏混合案卷运行已经证明：提供方可以返回语法有效的 JSON，但字段、绑定值或任务结构仍可能不满足本项目的严格计划契约。即使提示中加入完整 JSON 样例，同一 `PLANNER_INVALID_STRUCTURED_PROPOSAL` 仍可复现，导致 Agent 在读取材料前停止。

该失败不是放宽本地校验的理由。目标、案件快照、Skill、输入引用、依赖、风险和预算边界仍必须由代码验证；模型输出不能直接成为可执行任务图。

## 决策

仅对案件规划调用使用 DeepSeek 官方 Beta Chat Completions 端点，并通过一个强制的严格函数 `submit_case_plan_proposal` 接收候选计划：

- 请求固定 `strict: true`，并用 `tool_choice` 强制且只允许该函数；
- 函数参数 Schema 将 `schema_version`、`goal_hash`、`planning_snapshot_hash` 绑定为本次请求的唯一允许值；
- 每个任务使用一个按语义 Skill 划分的 `anyOf` 分支；`skill_id` 固定为该分支的唯一 Skill，`input_ref_ids` 只能选择当前规划快照中明确允许该 Skill 且可向提供方暴露的引用，`risk_hint` 不得超过服务器为该 Skill 固定的风险等级；当前没有兼容输入的 Skill 不进入提供方契约；
- 证据页的语义 Skill 授权同时绑定服务端登记的原件媒体类型：PDF 文本读取与台账提取仅接收 `application/pdf`，视觉 OCR 接收已支持的 PDF/JPEG/PNG；单页外部 OCR 向模型声明 `max_input_refs=1`，且本地编译器按服务器策略硬性拒绝超过一个引用。DeepSeek strict 数组不支持 `minItems/maxItems`，不得使用提供方不支持的数组整体枚举伪造该约束；
- 所有对象字段均为必填并禁止额外字段；返回必须是一个、且只能是一个完整函数调用；
- 该函数只是结构化输出信封，不对应执行器、网络工具、Shell、文件路径或外部动作；
- 函数 arguments 仍交给现有 `parse_case_plan_proposal` 和独立 Plan Compiler。依赖关系、Skill/输入兼容性、权限、预算、审批门及任务图仍由代码总控裁决；
- 请求继续执行“一次提交、结果未知不重试”的外部调用账本规则。Beta 端点拒绝、超时、非函数输出或本地编译失败均保守停止并留下审计状态。

材料数据路径没有扩大：仍是相同 DeepSeek 提供方、相同受控规划快照和相同脱敏验收案；普通文书、台账等适配器继续使用各自已固定的正式端点。本决策不授权向 Beta 规划端点发送真实客户原件，生产放行仍需单独的数据处理、稳定性与合同审查。

## 后果

- 好处：提供方先按 Schema 约束输出，减少“JSON 有效但计划结构无效”的运行时失败，同时不削弱本地总控。
- 代价：严格函数模式依赖 Beta 端点，接口稳定性低于正式端点；Worker 启动配置、运行预检和真实验收必须明确区分该通道。
- 约束：若严格函数模式不可用，不自动回退到文本 JSON，也不在同一运行中改用其他模型或重复提交。

## 被拒绝的方案

- 放宽 `parse_case_plan_proposal` 接受未知字段、错误绑定或模型自创 Skill：拒绝，因为会把提供方格式漂移转化为执行权限漂移。
- 对失败响应自动追加提示并重试：拒绝，因为可能在结果不明或计费已发生时重复调用，也会掩盖真实运行能力。
- 把规划函数直接映射为工具执行：拒绝，因为模型只能提出语义候选，不能绕过 Plan Compiler 和审批门。
